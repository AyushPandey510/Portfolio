01

Why I built it

Every time I needed to move a file from a lab computer to my phone, the options were to log in to something, mail it to myself, or find a cable. All I wanted was to say six characters out loud and have the other person type them.

So SwiftShare does one thing: you upload a file and get a short code, a link and a QR code. The other person uses any of the three. The file disappears after 24 hours, or after the number of downloads you chose, whichever comes first.

One job, three ways to receive, nothing to sign up for.

02

The architecture

Three clients talk to one Rust service. The service keeps metadata in SQLite and file bytes on disk, and two background tasks run beside the API in the same process.

03, the hard part

Never hold a whole file in memory

A naive upload handler reads the request into memory and then writes it out. With a 250 MB limit and a few people uploading at once, that is a server that falls over. SwiftShare streamsMoves data in small pieces as it arrives, instead of loading all of it first. both ways: the multipart body is written to disk chunk by chunk, and downloads are read from disk in chunks straight into the response.

The proof is in the measurements below: a 200 MB file went up and back down with an identical checksum while the server's peak memory moved from 11.5 MB to 14.9 MB.

Six characters, checked three ways

backend/src/main.rs

fn generate_file_code() -> String {
    rand::thread_rng()
        .sample_iter(&Alphanumeric)
        .map(char::from)
        .map(|c| c.to_ascii_uppercase())
        .filter(|c| c.is_ascii_alphanumeric())
        .take(6)
        .collect()
}

Uppercasing makes codes easy to read aloud and leaves 36 symbols, so there are about 2.2 billion codes. Before a code is used, the server checks that no live upload in memory, no row in SQLite and no file on disk already has it.

04

A file's journey

1
SendertoAPI

POST /api/upload as multipart, with the file and a download limit from 1 to 10.

2
APItoDisk

Stream the file to disk in chunks, then pick an unused 6-character code.

3
APItoSQLite

Save code, filename, size, expiry and limit. Return code, link and QR.

4
ReceivertoAPI

GET /api/download/:code. The API checks expiry and the download limit, then adds one to the count.

5
APItoReceiver

Stream the file back with no-store caching and nosniff headers.

6
SweepertoDisk

Every 60 s, delete files that have expired or used up their downloads.

08

What I'd change next

Rate-limit code lookups

2.2 billion codes is plenty for typing, not for a bot. Per-IP limits on /api/file and /api/download come first.

Encrypt at rest

An AES-256-GCM module is already in the repo but not on the upload path yet. Wiring it in is a small change.

Object storage

S3 or R2 with signed URLs, so files survive redeploys and more than one instance can serve them.

Resumable uploads

Mobile networks drop. Chunked, resumable uploads would stop a 200 MB upload restarting from zero.
