01

Why I built it

My bank already tells me about every rupee I spend, one SMS at a time. The information is all there on my phone; it's just unreadable as a whole.

XpenseCalc reads those messages on the device, turns them into transactions, and shows where the money went: by day, by bank, debit against credit. You can add cash expenses by hand, keep wallets, and export a PDF report to share.

Your bank already writes your expense diary. This app just reads it.

02

The architecture

Everything runs on the phone. Flutter can't read SMS by itself, so a small Kotlin plugin reads the inbox and hands raw messages to Dart over a method channel.

03, the hard part

Every bank writes its own language

There is no standard for bank SMS. Offers look like transactions, failed payments look like successful ones, and one message can say both "debited" and "credited". So the parser is a funnel: each stage either passes the message on or rejects it with a named reason, which makes every miss debuggable.

The message that says both things

Two real formats from Indian banks say debited and credited in the same message. Checking for "credited" first, the obvious approach, turns both of these payments into income:

Dr. from A/C XX1234 and Cr. to payee@upi

Debit: "Dr." comes first

A/c debited Rs.250 & credited to merchant

Debit: "debited" comes first

Banks state the account holder's own action first and the other party's second. So when both words appear, the parser trusts whichever comes earliest.

lib/services/sms_service.dart, _determineTransactionType

final creditMatch = RegExp(
    r'\b(cr\.?|credited|deposited|received|refund)\b',
    caseSensitive: false).firstMatch(body);
final debitMatch = RegExp(
    r'\b(dr\.?|debited|withdrawn|charged)\b',
    caseSensitive: false).firstMatch(body);
if (creditMatch != null && debitMatch != null) {
  return creditMatch.start < debitMatch.start ? 'credit' : 'debit';
}

Reading the inbox twice shouldn't double your spending

The app rescans the inbox every time it opens. A unique indexA database rule that refuses a second row with the same values in the chosen columns. on sender, amount, date and type means a transaction that's already stored is simply skipped.

05

What I'd change next

A test corpus

Anonymised real messages per bank, with the expected result, so a parser change can't silently break one bank.

Merchant categories

Group spending into food, travel and bills from the payee name, on the device.

Statement import

Import PDF statements, so iPhone users and older history are covered too.

Optional encrypted backup

Export an encrypted file to move data to a new phone without a server.
