01

Why I built it

Many web vulnerabilities come down to memory mistakes, data races and unchecked input. Rust rules out the first two at compile time. For my paper I wanted to test that claim on something real, so I built a complete shop backend: users, products, orders, payments and password resets.

A paper is more convincing when there's a running system behind it.

02

The architecture

03, the hard part

Two buyers, one item left

Placing an order touches several tables: check each product, total the price, create the order, record each line, and reduce stock. If any step fails halfway, the shop ends up with an order nobody paid for or stock that never comes back. So the whole thing runs in one transactionA group of database changes that either all happen or none do..

1
Order service

Begin a transaction.

2
Order servicetoPostgres

For each item, load the active product, check there's enough stock, and add to the total in paise.

3
Order servicetoPostgres

Insert the order, then each line with the price at the moment of purchase.

4
Order servicetoPostgres

UPDATE products SET stock = stock - quantity.

5
Order service

Commit. Any error before this point rolls everything back.

Now two people buy the last item at the same moment. Both read a stock of 1, and both pass the check in step 2. What stops the shop selling two is the database itself: the products table has CHECK (stock >= 0), so the second UPDATE would take stock to −1 and Postgres refuses it. That transaction rolls back, and nothing is oversold.

What the losing buyer sees today

A generic error rather than a clear "sold out". The data stays correct, but the message doesn't. Making the stock update conditional fixes that; it's first in section 06.

04

Data model

Money is stored as whole paise, never as floating point, and the database checks the rules the code also checks.

products

price_cents  INTEGER  CHECK (>= 0)
stock        INTEGER  CHECK (>= 0)

The stock check is what makes the race safe.

orders

user_id → users
status, total_price_cents
shipping_address

One row per checkout.

order_items

order_id → orders (cascade)
product_id → products
quantity CHECK (> 0)
price_at_purchase_cents

Keeps what the buyer actually paid, even if the price changes later.

password_resets

user_id → users (cascade)

Reset requests tied to a user and deleted with them.

06

What I'd change next

A clear "sold out"

UPDATE … WHERE stock >= quantity, and return a 409 when no row changes, instead of a generic error.

Razorpay's signature scheme

Verify webhooks with HMAC-SHA256 as Razorpay signs them, using a constant-time comparison.

Idempotent checkout

An idempotency key per checkout, so a retried request can't create a second order.

Limits beyond login

Rate limits on registration and password resets too.
