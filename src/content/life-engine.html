01

Why I built it

When I asked a chatbot whether to take an internship or keep building projects, it gave the same balanced answer it would give anyone. It didn't know what I'd already built, what I was good at or what I'd said I wanted.

Life Engine starts from you. You set goals, habits and a few personality traits, and upload your résumé, cover letters and certificates. Then you talk to your future self: an AI that answers with your context, and can compare two decisions side by side.

Advice is only as good as what it knows about you.

02

The architecture

A React app talks to a FastAPI service. Postgres holds the durable data, Redis holds counters and cache, Celery runs slow work in the background, and each user gets their own FAISS index file.

03, the hard part

What goes into each prompt

Sending every document with every message is slow, costly and drowns the question. Sending none makes the AI generic again. For each message the AI service scores every document you've uploaded and only injects the ones that clear a threshold.

The scorer takes two passes and keeps the higher score. The first looks for intent: a question about skills or experience lifts documents that actually have those sections. The second counts words the question shares with a document's skills, keywords and opening text.

Where FAISS fits today

Uploaded documents are embedded into your own FAISS index, and the retrieval function is written. Chat doesn't call it yet; it uses the scorer above, which needs no extra API call per message and is easy to explain. Mixing in vector search is the first item in section 07.

04

Teaching it your documents

1
ApptoAPI

Upload a résumé, cover letter, certificate or note. Up to 5 MB.

2
Document service

Check the type, then parse it: pypdf for PDF, python-docx for DOCX, plain decoding for text. Keep the first 20,000 characters.

3
Document service

Extract signals: skills, experience, education, certifications, projects and keywords.

4
APItoPostgres

Save the document and merge its signals into your profile.

5
Memory servicetoFAISS

Embed the text in chunks, normalise the vectors and add them to your index, so inner product equals cosine similarityHow closely two vectors point the same way. 1 means the same meaning, 0 means unrelated..

05

When things break

IfWhat happensWhy it's built this way
The AI provider is downChat returns a polite fallback and still saves the turn.A third-party outage shouldn't look like my outage.
Redis is downRate limiting is skipped and logged; requests carry on.Fail open: availability matters more than strict limits here.
Embedding fails in productionThe error is raised and logged. Development falls back to a fixed mock vector.Never store fake vectors in real users' indexes.
Anything else throwsThe database rolls back and the user gets a clean 500 message.No half-saved conversations.

Decisions and what they cost

I choseOverBecauseIt costs
Groq with Llama 3.1 8BA larger hosted modelFast, cheap replies that stream.Less depth on hard questions.
One FAISS file per userA shared vector databaseHard isolation; deleting a user deletes one file.Lives on one server's disk.
A keyword scorer in chatVector search per messageNo extra API call, and every choice is explainable.Misses synonyms.
Rate limit that fails openFailing closedA Redis blip shouldn't lock everyone out.No limits while Redis is down.

07

What I'd change next

Hybrid retrieval in chat

Call the existing retrieve_memories() and merge its results with the keyword scores, so synonyms count.

Vectors in Postgres

pgvector instead of files on disk, so memory survives redeploys and scales past one server.

Rate limit by user

Key the limit on the signed-in user, not the X-Forwarded-For header, which a client can set.

Stream to the screen

The backend already streams from Groq; passing it through would show the first words sooner.
