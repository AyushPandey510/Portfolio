01

Why I built it

Group chats outlive the places that created them. The people at a concert, a campus canteen or a hackathon floor share a moment, then a group chat drags on for months with half of them gone. I wanted the opposite: a room that exists only for the people standing in it, with no names and no history of where you've been.

That gives one hard requirement. If presence decides access, then a modified app must not be able to claim it is somewhere it isn't. Everything else in the design follows from that.

The phone can be fast. The server has to be right.

02

The architecture

One Rust binary holds the REST API, the WebSocket hub and two background workers. The first version runs as three containers: nginx, the API and Postgres. Every box below is a real module in the repo.

03, the hard part

GPS lies. The engine has to decide anyway.

A phone lying on a table reports positions that wander by tens of metres, and a spoofing app can report anything at all. Every location fix goes through six pure functions. Each one is unit tested on its own, and the numbers below are the real constants from the code.

Step 5 is where most of the thinking went. With a single threshold, someone standing at the edge of a room flips between inside and outside every few seconds. The engine uses hysteresisUsing a different threshold to leave than to enter, so a value hovering at the line doesn't flip back and forth.: you are in at 100 m, but you are only out past 120 m, and only after three readings in a row agree.

apps/backend/src/geofence/hysteresis.rs

pub const EXIT_BUFFER_METERS: f64 = 20.0;
pub const REQUIRED_OUTSIDE_READINGS: usize = 3;

pub fn buffered_outside_decision(
    raw: GeofenceDecision,
    consecutive_outside: usize,
) -> (GeofenceDecision, usize) {
    match raw {
        Outside => {
            let next = consecutive_outside + 1;
            if next >= REQUIRED_OUTSIDE_READINGS {
                (Outside, next)
            } else {
                (NearBoundary, next)
            }
        }
        Inside | NearBoundary => (raw, 0),
        _ => (raw, consecutive_outside),
    }
}

Why a median and not an average

One bad fix 200 m away drags an average far off and kicks the user out of the room. The median of four readings simply ignores a single spike.

Why pure functions

There is no database, clock or network inside the engine. That makes every rule a fast unit test, and the same rules are mirrored in Dart so the phone can show the right state before the server answers.

Joining a Space, step by step

What happens between the tap and the first message, read from join_space in spaces.rs.

1
PhonetoAPI

POST /spaces/:id/join with latitude, longitude and accuracy.

2
APItoPostgres

Load the Space: centre, radius, visibility. Private Spaces need a valid invite code.

3
APItoPostgres

Is there already an active or grace session? If so, reactivate it and return.

4
APItoGeofence engine

validate(fence, fix). Only Inside or NearBoundary may join; anything else gets 403.

5
APItoPostgres

INSERT the session ON CONFLICT DO UPDATE, RETURNING (xmax = 0) to learn whether it was a new row.

6
APItoPostgres

Only if it was new: member_count + 1.

7
APItoPhone

The session: a random anonymous name and an expiry time.

Step 5: why xmax = 0

Two taps on Join can arrive at the same moment. The upsertInsert a row, or update it if it already exists, in one statement. lets Postgres pick one winner, and only a brand-new row has xmax = 0. So the API counts the member exactly once without taking a lock.

05

Data model

Two schemas: identity for who, activity for what happens. The rules that must hold under concurrent requests live in the database as partial unique indexes, not in Rust.

identity.users

id uuid
device_id_hash text, unique

HMAC-SHA256 of the device ID. Migration 0008 backfilled old rows.

identity.refresh_tokens

token_hash, user_id
expires_at, revoked_at

Only the hash is stored, so a leaked table can't mint sessions.

activity.spaces

created_by, latitude, longitude
radius_meters 1–300 (CHECK)
archived_at

Unique: one active Space per creator.

activity.sessions

user_id, space_id, anonymous_id
status active | grace | expired
expires_at

Unique: one anonymous name per Space while not expired.

activity.messages

space_id, created_at, anonymous_id
moderation_status

Index (space_id, created_at DESC) serves chat history.

location_validation_events

distance_bucket, accuracy_bucket
precise_location_expires_at

Migration 0007 replaced raw coordinates with buckets. Precise values expire.

When things break

Read from the code, not assumed. The last column is what I would add next.

IfWhat happens todayWhat I would add
Postgres is unreachableRequests return 500, but each can wait up to 30 s (sqlx's default) for a connection first.A 2 s acquire timeout and a readiness check, so it fails fast.
A phone's socket dropsThe app reconnects with backoff: 0.5 s, doubling up to 8 s.Missed events aren't replayed: fetch history since the last message id.
A subscriber falls behindEach room buffers 256 events; a lagging socket skips what it missed.Send that client a resync event.
Moderation backs upThe queue holds 256 jobs; when it is full, sending waits. Backpressure, not data loss.Queue depth as a metric, with an alert.
The API restartsRoom channels vanish from memory; sessions live in Postgres, so clients reconnect and carry on.Fan-out across instances (section 09).
Someone walks awayThree outside readings, 120 s of grace, then the 30 s worker expires the session.Working as designed.

09

At a million users, I would change this

Next 1: fan out across instances

Past the measured knee: Redis pub/sub or NATS per room, so any instance can serve any socket.

Next 2: real spatial indexing

The bounding box gave 71×. PostGIS and a GiST index come next, for any fence shape.

Next 3: location write volume

Batch validation events and partition them by day.

Next 4: smarter moderation

A trained classifier behind the same queue, plus per-device rate limits.
